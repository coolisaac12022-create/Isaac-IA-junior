01 — INJECTION SQL : CONTOURNER UN LOGIN

DIFFICULTÉ : ★☆☆☆☆ — DÉBUTANT

Le formulaire de connexion de megashop.local (fictif) construit cette requête derrière le rideau :
SELECT * FROM users WHERE user='…' AND pass='…'
Les champs sont recopiés brut dans la requête. À vous de trouver une entrée qui rend la condition toujours vraie et débloque l'accès admin.

FORMULAIRE DE CONNEXION — MEGASHOP.LOCAL
En attente de la tentative…
INDICE : essayez dans le mot de passe : ' OR 1=1 --
Le ' ferme le champ, OR 1=1 rend la condition vraie pour toutes les lignes, et -- transforme le reste de la requête en commentaire. Variante : utilisateur admin' -- avec n'importe quel mot de passe.
COMMENT S'EN PROTÉGER : jamais de requête « collée » — utiliser des requêtes préparées (paramètres bindés), valider le format des entrées, et un compte base de données en lecture seule pour l'app web. C'est la faille n°1 historique du top OWASP.

02 — XSS : VOLER LE COOKIE DE SESSION

DIFFICULTÉ : ★★☆☆☆ — DÉBUTANT+

Le livre d'or de blog-isaac.local (fictif) affiche ce que vous tapez sans aucun filtrage. Injectez du JavaScript qui s'exécute dans la page de la victime. Objectif : faire partir le cookie de session SESS=abc123admin vers votre « serveur » fictif.

LIVRE D'OR — BLOG-ISAAC.LOCAL
INDICE : le site recopie votre texte en HTML brut. Testez d'abord
<b>test</b> — il s'affiche en gras, preuve que le HTML passe. Ensuite :
<script>volerCookie("SESS=abc123admin")</script>
COMMENT S'EN PROTÉGER : échapper toute sortie HTML (transformer < en &lt;…), bannir innerHTML sur des données utilisateur (utiliser textContent), et activer une Content-Security-Policy qui interdit les scripts inline.

03 — COMMAND INJECTION : LE PING QUI EXÉCUTE

DIFFICULTÉ : ★★☆☆☆ — DÉBUTANT+

L'outil réseau de panel.hote.local (fictif) lance sur le serveur :
ping -n 1 [votre entrée]
Sur Windows, & et | enchaînent les commandes. ICI LE SERVEUR EST UNE SIMULATION : il ne répond qu'à une liste de commandes inoffensives. Faites-le parler.

OUTIL PING — PANEL.HOTE.LOCAL
$ outil prêt. Entrez une cible.
INDICE : la simulation accepte après un & ces commandes factices : whoami, ipconfig, net user, echo, dir.
Exemple : 127.0.0.1 & whoami puis 127.0.0.1 & net user
COMMENT S'EN PROTÉGER : ne jamais coller une entrée utilisateur dans une ligne de commande shell. Utiliser execFile/argumentaires séparés (pas de shell), valider la cible contre un format strict (une IP ou un hostname, rien d'autre).

04 — IDOR : CHANGER UN NUMÉRO DANS L'URL

DIFFICULTÉ : ★☆☆☆☆ — DÉBUTANT

L'espace client de factures.local (fictif) montre VOTRE facture à l'adresse /facture?id=7. Le serveur ne vérifie pas si la facture appartient au client connecté — juste le numéro. Trouvez la facture cachée de l'administrateur.

ESPACE CLIENT — FACTURES.LOCAL (connecté : isaac, id 7)
Sélectionnez une facture ou modifiez l'URL.
INDICE : les ID font 1 à 9. L'admin est probablement un petit numéro… essayez ?id=1. Les boutons ci-dessous sont les factures « autorisées » — l'URL, elle, n'est pas bloquée.
COMMENT S'EN PROTÉGER : vérifier côté serveur que la ressource demandée appartient à l'utilisateur connecté (contrôle d'accès sur chaque requête), et utiliser des identifiants non devinables (UUID) — qui ne remplacent pas le contrôle, mais complètent.

05 — MOTS DE PASSE : L'ATTAQUE DICTIONNAIRE

DIFFICULTÉ : ★★☆☆☆ — DÉBUTANT+

Un routeur box.local (fictif) protège son admin par un mot de passe parmi ceux de la liste de droite (une « wordlist »). Un script essaie chaque mot à la suite. Chronométrez l'attaque, puis trouvez la parade.

PANNEAU ROUTEUR — BOX.LOCAL
Progression 0%
$ en attente…
INDICE : le mot cible est le 12ᵉ environ de la liste. La vraie leçon est dans le calcul : un mot de passe de 6 caractères lowercase = 26⁶ ≈ 300 millions de combinaisons → quelques heures pour une machine.
12 caractères avec majuscules, chiffres, symboles = plus de 7×10²⁴ → des millénaires. La longueur est votre bouclier.
COMMENT S'EN PROTÉGER : mot de passe long (phrase de 4 mots minimum), différents partout, stockés dans un gestionnaire, et double facteur (2FA) activé — même cassé, le compte reste fermé. Côté serveur : limiter les tentatives (rate limiting).
